# v0.2 polish — Open With, New File, menu separators, app icon

## Context

v0.2 (see `2026-05-11-v0.2-configurable-actions.md`) shipped the configurable-actions architecture and six actions. Manual testing surfaced four polish issues that block a clean v0.2 release:

1. **Open With** launches the IDE but doesn't open the target folder in it.
2. **New File** is unresponsive — clicking it does nothing.
3. The single auto-inserted separator between Copy Path and Open With looks like a missing item; its placement doesn't match a clear mental model.
4. `termhere.iconset/` exists in the repo root with the standard 10 PNGs but isn't wired into the build, so the app uses the generic macOS icon.

A fifth question — whether per-action menu icons should be redrawn as custom assets — was answered "no": SF Symbols + the system-rendered app bundle icons (for Open With sub-items) are sufficient. No code change there.

## Goals

- Open With opens the IDE **at** the target folder for the bundled presets (VSCode, Cursor, Sublime, iTerm, Warp, Ghostty).
- New File reliably creates the file and reveals it in Finder. Any failure is logged with cause.
- Menu separators reflect three semantic groups (launch / clipboard / file ops) instead of an implicit "top-level vs submenus" boundary.
- The built app uses the icons in `termhere.iconset` in Dock, Finder, and the About panel.

## Final menu shape

```
Right-click → TermHere ▸
  Open Terminal Here
  Open With       ▸
  Run in Terminal ▸
  ─────────────
  Copy Path
  ─────────────
  New File        ▸
  Move To         ▸
```

A separator is rendered **between** two non-empty groups. An entirely empty group (e.g., Move To has zero configured destinations and no other action is in its group — won't happen with the layout above) is skipped without leaving an orphan separator.

## §1 — Open With opens the folder

### Root cause

`OpenWithAction.swift` uses `NSWorkspace.openApplication(at:configuration:)` with `configuration.arguments = ["{path}"]`. That API launches the app and passes the strings as process `argv`. GUI editors (VSCode, Cursor, Sublime) don't read `argv` to decide what folder to open — they expect either:

- the macOS LaunchServices "open these URLs *with* this app" call (equivalent to shell `open -a "Visual Studio Code" /path`), or
- the editor's CLI shim (`code /path`, `cursor /path`) which itself translates to the LaunchServices call.

### Fix

Switch to `NSWorkspace.open(_ urls:, withApplicationAt:, configuration:)`:

```swift
let config = NSWorkspace.OpenConfiguration()
config.activates = true
NSWorkspace.shared.open(
    [context.targetDirectory],
    withApplicationAt: appURL,
    configuration: config,
    completionHandler: nil
)
```

### Schema change

`OpenWithEntry.args` becomes vestigial — the path is now an opened URL, not an argv entry. All six bundled presets drop the `"args"` field. The Codable definition changes from `let args: [String]` to `var args: [String]? = nil`, so:

- Bundled and new presets without the field decode cleanly.
- Existing user JSON containing `"args"` still decodes; the value is simply ignored at runtime.

Resulting preset shape:

```json
{ "title": "Visual Studio Code", "bundleId": "com.microsoft.VSCode" }
```

### Considered and rejected

Keeping `args` as a way to pass extra launch flags to power users. Rejected — no current demand, and `{path}` substitution in `args` becomes confusing once the path is also passed as an opened URL. If a real need surfaces later, add a separate `extraArguments` field.

## §2 — New File creates the file

### Root causes

Two compounding issues in `NewFileAction.run`:

**(a) Silent failure.** The write line is `try? body.data(using: .utf8)?.write(to: target)`. Both the `data(using:)` and `write(to:)` failures are swallowed without a log — the action returns immediately and the user sees nothing.

**(b) Missing sandbox entitlement on the Finder extension.** `TermHere.entitlements` includes `com.apple.security.files.user-selected.read-write`; `TermHereFinder.entitlements` does not. The Finder Sync extension is granted read access to URLs vended by `FIFinderSyncController`, but **creating a new file** at a user-chosen location requires `files.user-selected.read-write` even though the URL came from Finder. Without it, `Data.write(to:)` returns a permission error which is then dropped by `try?`.

### Fix

1. Add `com.apple.security.files.user-selected.read-write` (value `true`) to `TermHereFinder.entitlements`.
2. Rewrite the write block with explicit error handling:

   ```swift
   guard let data = body.data(using: .utf8) else {
       os_log("New File: could not encode body as UTF-8", log: Self.log, type: .error)
       return
   }
   do {
       _ = context.targetDirectory.startAccessingSecurityScopedResource()
       defer { context.targetDirectory.stopAccessingSecurityScopedResource() }
       try data.write(to: target, options: .atomic)
   } catch {
       os_log("New File: write failed at %{public}@: %{public}@",
              log: Self.log, type: .error, target.path, String(describing: error))
       return
   }
   NSWorkspace.shared.activateFileViewerSelecting([target])
   ```

   Wrapping in `startAccessingSecurityScopedResource()` is no-op when not needed and required when the Finder-vended URL comes with a sandbox extension. Safe in both cases.

3. Apply the same `startAccessing... / stopAccessing...` pattern to `MoveToAction.run` for the source URLs (`context.selectedItems`) so the move doesn't silently fail under the same sandbox condition. `MoveToAction` already has a `do/catch` with logging, so no logging change there.

### Verification

After fix, with the host app re-signed and the extension re-enabled:

- Right-click a folder → New File → Markdown → `Untitled.md` appears in that folder with content `# Untitled\n\n`. Finder highlights the new file.
- Right-click again → New File → Markdown → `Untitled 2.md`.
- Console.app filtered to subsystem `com.termhere.TermHere.Finder` shows zero error lines on the success path, and a clear cause if a write does fail.

## §3 — Menu separators by semantic group

### Fix

Replace `ActionRegistry.actions: [Action]` with `groups: [[Action]]`:

```swift
enum ActionRegistry {
    static let groups: [[Action]] = [
        [OpenTerminalAction(), OpenWithAction(), RunCommandAction()],
        [CopyPathAction()],
        [NewFileAction(), MoveToAction()],
    ]
}
```

Rewrite `MenuBuilder.build` to:

1. For each group, compute the list of menu items it would emit (top-level item for `Action`, submenu for `GroupAction` whose `loadItems` is non-empty, otherwise nothing).
2. Skip a group entirely if it would emit zero items.
3. Between two adjacent non-empty groups, insert a single `.separator()`.

The current "between top-level and group submenus" detection logic is removed.

`MenuBuilder.build`'s signature stays the same — `clickableActions: inout [Action]` is still appended-to as items are emitted, indexed by `tag` exactly as today. `FinderSyncController` needs no change.

### Considered and rejected

A flat list with a marker `SeparatorAction` element. Rejected — `[[Action]]` makes group-emptiness trivial to check without special-casing the marker, and keeps the data structure declarative.

### Verification

- Default install with all bundled presets → menu shows three groups separated by lines in the order above.
- Delete every file under `~/Library/Application Support/TermHere/move-to/` (the default) → New File ▸ still renders, Move To ▸ is absent, the group still appears (because New File is non-empty), no orphan separator.
- Right-click in container with no selection → Move To's `isAvailable` returns false, only New File renders in group 3, separators around group 3 still correct.

## §4 — Wire app icon into the build

### Current state

`termhere.iconset/` sits at `/Users/shenwei/code/TermHere/termhere.iconset/` (repo root) containing the canonical 10 PNGs (`icon_16x16.png` through `icon_512x512@2x.png`). It is not referenced by `project.yml`, and the workspace has no `Assets.xcassets`. The built `TermHere.app` uses the generic macOS app icon.

### Fix

1. Move `termhere.iconset` into `TermHere/Assets.xcassets/AppIcon.appiconset/` with a generated `Contents.json` that maps each PNG to its `idiom: mac` / `size` / `scale` slot.
2. Add `TermHere/Assets.xcassets/Contents.json` (root).
3. In `project.yml`, under the host app target's `sources:`, add `TermHere/Assets.xcassets`. Set `settings.base.ASSETCATALOG_COMPILER_APPICON_NAME: AppIcon`.
4. Regenerate the Xcode project with xcodegen.

### Verification

- `xcodebuild -showBuildSettings` for the host target lists `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon`.
- Built `.app` shows the custom icon in Finder, Dock, and About panel.
- Finder extension target unaffected (extensions inherit the host icon).
